# 2026-11 第三轮调研：会议纪要与录音总结的产品化能力

> 目的：前两轮（`landscape-2026-11.md`、`landscape-2026-11-r2.md`）聚焦识别引擎与模型格局，
> 本轮转向纪要提炼与交付形态，回答「识别已经不落后，纪要这段还差什么」。
> 方法：GitHub 同类项目 + 2026 年会议摘要评测论文 + 回本项目代码逐条核实。
> 收录标准：结论必须能指到代码行、仓库或一手论文；拿不到证据的标「未核实」。

## 一、结论先行

1. **短板不在识别，在纪要的质量闭环。** 识别侧本项目已到第一梯队（中文 ITN、规范 docx、RTTM、
   缓存键、声纹库），但纪要产出后既没有机器可读形态，也没有任何自动核验。
2. **外部最值得抄的不是功能清单，是三条工程约束**：结构化 sidecar、模板可编辑、说话人改名
   不重建转写。这三条都不需要换模型。
3. **与 2026 年的摘要评测对照，纪要最大的风险不是事实错，是三类语用错**：过度自信的转述
   （27.3%）、无依据的量化（16.9%）、说话人张冠李戴（16.0%），合计超过六成
   （MeetingProbe，1049 条失败归因）。
4. **本轮的三个改动都是「已有能力没接上」**，不是新增能力：`--export` 早已存在但无人调用、
   `names` 被错误计入缓存键、校验器从未进出稿流程。

## 三、质量评测口径（可机械判定的部分）

2026 年这条线的共识是分两层，不能混在一层判：

**第一层：机械可判定**（适合 CI 门禁）

| 指标 | 定义 | 门槛 |
|---|---|---|
| 编造数字 | 纪要出现、原文（剥时间戳后）找不到的数字个数 | 0 |
| 数字溯源率 | 纪要数字中能在原文找到的比例 | ≥ 0.5 |
| 责任人溯源率 | 待办责任人能在原文找到的比例 | ≥ 0.8 |
| 必填节齐全度 | 四个必填节是否都在 | 1.0 |

**第二层：需读语义**（不进门禁，列入 `unjudged`）

- 语义忠实度：是否曲解原意
- 无依据量化：把模糊表述写成精确数字
- 说话人张冠李戴：归属错人
- 语用过信：把推测写成事实

第二层若强行机械判定，会把同义改写误判成编造。可用路线（均未落地，需先验证收益）：
LLM-as-judge 校准（MARC 口径 faithfulness/completeness 双维 1-5 分，Spearman 0.66-0.73）、
RAGTruth 类 span 级标注、SIEVE 的七类信息角色留存（topic/outcome/action-detail 留存率高，
background/concerns/未决项更容易被丢）。

## 四、一处实测踩到的反例（写进门槛设计）

真实素材（2026-11-18，23 分钟会议）跑首版评测时，「12 元至 16 元」被判编造。
根因不是纪要错，是原文用中文数字写「十三四块、十五六块」，纪要做忠实整理写成了阿拉伯数字。
只比对阿拉伯数字的口径会把正常整理判成幻觉——这类误报会让人直接不信门禁。

修法是 `_cn_numbers` 把中文数字展开成候选值（「十五六」→ 15/16、「十三四」→ 13/14）。
展开必须收窄：早期版本把「十五六」也展开出 50/55/56，等于放水，等于门禁失效。
两者都是过度宽松或过度严格导致的失效，方向相反、后果相同。

## 五、明确不采纳

| 候选 | 理由 |
|---|---|
| 引入 LLM 生成纪要入库（管线自己写纪要） | 纪要需要人/agent 判断，管线只产原文；生成入库会把不可复现的东西塞进交付物 |
| 向量检索替换 FTS5 | 现无真实查询日志支撑；trigram 对中文专名已够用 |
| 实时字幕与会议机器人 | 需重构主干，前两轮已判定不做 |
| 声纹注册做成产品流程 | 合规压力（生物特征）大于技术收益；现有 `--speaker-db` 够本机用 |
| 用 20B 级本地模型直接出纪要 | millet 自评：低信息密度转写（「嗯」「好」为主）上会幻觉，且长中文稿易超时 |
